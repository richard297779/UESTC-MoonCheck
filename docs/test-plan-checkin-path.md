## 3. 每个测试的详细做法

### T1 · 浏览器"点图标"请求序列观测 ★最关键

**目的**：搞清"从平台首页点晚安成电图标"这一次导航，与我们程序化发的 `checkLogin` 请求之间有什么差异（前置请求？一次性 token？特殊头？）。

**步骤**：
1. 用**未登录状态**的浏览器（新开隐私窗口，或先删掉 `jzsz.uestc.edu.cn` 的 `SESSION` Cookie）；
2. F12 → **网络(Network)** → 勾选 **"保留日志(Preserve log)"** → 点 🚫 清空记录；过滤器选 **All**（不要选 Fetch/XHR，我们要看文档导航）；
3. 正常访问 `https://jzsz.uestc.edu.cn/` → 完成登录（到首页）；
4. **点击"晚安成电"图标**，等打卡页面出来；
5. 在 Network 列表里找到点击之后出现的那几条请求，**右键列表空白处 → Export all with HAR content → 保存 .har 文件**（或至少截图：列表 + `checkLogin` 那条的"标头"面板）。

**我要看什么（结果→结论映射）**：

| 观察点 | 若如此 | 结论 |
| --- | --- | --- |
| 点图标后，`checkLogin` **之前**还有一个 XHR（如 `/portal/...open`、`/api/auth/...`） | 有 | **A 可行**：固件在登录成功后照抄这个请求，再 `checkLogin` |
| `checkLogin` 的 URL 带了额外参数（`token=`、`sign=`、时间戳…） | 有 | **A 可行**：复刻参数生成逻辑（取决于参数来源） |
| `checkLogin` 请求头里有我们没发的东西（非 Cookie 的自定义头） | 有 | **A 可行**：补头 |
| 以上全无，请求与我们发的**逐字段一致**，但浏览器能进 | 无差异 | **A 判死** → 走 B（差异在浏览器内核本身，见 T3） |

### T5 · SESSION 生命周期测量（我执行，白天挂机）

**目的**：精确回答两个问题——① 授权会话的绝对寿命多长？② 持续使用会不会滑动续命？
（这决定 B 的伴生程序是"每天登录一次"还是"打卡前 10 分钟登录一次"，也决定设备日常保活请求有没有续命作用。）

```powershell
# 浏览器登录一次，把 SESSION 填入 config.json 后：
python diag_ttl.py --interval 300            # 只观测：每 5 分钟测一次，直到被拒
python diag_ttl.py --interval 300 --activity # 对照组：每轮顺带 GET 首页（模拟正常使用）
```
输出是一条时间线（`+Ns checkLogin=H5/首页 today=code`），最后一行给出**存活时长**。两轮对比即可判定是否滑动。

## 5. 安全红线（B 架构新增）

| 风险 | 对策 |
| --- | --- |
| 局域网 HTTP 传 SESSION = 传账号通行证 | 端点必须带**预共享随机 token**（配网时 BLE 写入设备与伴生程序各一份）；只监听 `127.0.0.1` 或内网段；**不开公网、不写日志** |
| 伴生脚本存账号密码 | 复用 `config.json`（已 gitignore）；B2 模式则**完全不存密码**（只读 Cookie） |
| HAR/Cookie 文件外泄 | 用完即删；`.gitignore` 已覆盖 `capture/`、`config.json`、`out/` |

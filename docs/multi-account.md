# 多人打卡

一块板子可以替**同宿舍的几个人**打卡。设备里有一张账号表，每个账号独立开关，
每晚会按顺序逐个执行。

> ⚠️ 使用前提：**每一位账号持有者都必须知情并明确同意**。
> 不要把别人的学号密码偷偷填进来——这既是账号安全问题，也可能违反校规。

---

## 添加账号

0.8.0 Android / 电脑 GUI 支持新建和合并修改。新账号必须填写标签、学号、密码、32 位指纹；修改通过标签、序号或完整学号唯一匹配，非空项才更新，空项保留原配置。经纬度成对修改，地址可单独修改。新建位置留空采用设备保存的默认位置。需配套支持 `account-v2` 的 0.8.0 固件，旧发行固件需升级。

以下 CLI 仍采用历史整条覆盖语义，不提供新版留空保留；修改已有账号建议使用图形界面。

```text
account add A01 <学号> <密码> [指纹|-] [纬度 经度 [地址…]]
```

- 标签只允许 1–12 位字母、数字、`-` 或 `_`，如 `A01`、`roommate_2`。
- 指纹位置填 `-` 表示这个账号不单独设指纹（大多数情况建议**每个账号都填自己的指纹**）。
- 坐标可省略——省略就沿用设备当前坐标（`loc` 配的那个）。
- 地址可省略，也可写多个词。

示例：

```text
account add A01 2023XXXXXXX pass1 0123456789ABCDEF0123456789ABCDEF
account add A02 2023YYYYYYY pass2 0123456789ABCDEF0123456789ABCDEF
account add A03 2023ZZZZZZZ pass3 - 30.753500 103.934200 四川省成都市郫都区
```

> 每个人的指纹都不同，必须各用各的（指纹 = 那台浏览器）。填错会报 `NEED_MFA`。

## 微信授权凭据（当前固件源码）

新版固件除了 CAS 登录所需的学号、密码和指纹，还需要每个账号本人授权的微信凭据，用来换取平台要求的打卡操作票据。获取步骤和扫码地址见[快速开始](quickstart.md#22-准备微信授权凭据)：每位账号持有人使用自己的微信扫码确认，然后从 DevTools 中 `static.pc.yyb.qq.com` 来源的 Cookie 读取凭据。仅使用下文列出的 `open.weixin.qq.com` 地址，不要从不明网站下载工具或扫描来路不明的二维码。

Cookie 中的 `openid`、`accesstoken`、`refreshtoken` 分别对应设备指令中的 `openid`、`access`、`refresh`。`expires_in` 是剩余秒数，不是 Unix 时间；将它加到当前 Unix 时间（秒）得到 `expiresAt`，或先填 `0` 让固件首次使用前刷新并保存实际到期时间。每个账号必须由账号本人完成扫码，不要互相转交令牌。复制 Cookie 后、导入开发板前，先关闭该账号的 QR Connect 页面；同一组凭据只能由一个客户端保活，避免扫码页面、其他程序与开发板同时刷新同一组令牌。多个账号请依次扫码、复制、关闭页面，再分别导入对应槽位。

微信凭据槽位按账号表顺序从 0 开始，与上面的账号排列对应。账号表为空、只使用设备主账号时用槽位 0。每个账号都应由账号持有人提供并授权：

```text
wx import 0 <A01的openid> <A01的accesstoken> <A01的refreshtoken> 0
wx import 1 <A02的openid> <A02的accesstoken> <A02的refreshtoken> 0
wx status
wx test 0
wx test 1
```

`wx status` 只显示槽位摘要，不回显令牌，也不会显示槽位对应的账号。新增账号会追加到表尾；删除账号会压缩账号表，之后账号的槽位可能改变。新版固件在删除或清空账号前清除全部微信凭据；修改学号会清除该槽位授权。之后都要按新的顺序重新导入需要的凭据，并逐个运行 `wx test <slot>`。微信授权令牌等同敏感登录凭据，会保存在设备 NVS 中；不要共享或提交到 Git。

## 查看与管理

| 命令 | 作用 |
| --- | --- |
| `account list` | 查看全部账号、开关状态、是否已配指纹 |
| `account on A01` | 启用 |
| `account off A01` | 暂停（保留配置，不参与打卡） |
| `account rm A01` | 删除 |
| `account clear` | 清空整张表 |

上限 **6 个**账号。设备里只保存明文，请勿转借。

## 每晚怎么执行

账号表非空时，设备按表顺序逐个执行「登录 → 门户预热 → 打卡 → 复查」。
账号之间默认间隔一段时间，避免同时请求。

```text
multi 30          # 设置账号间隔为 30 秒（0–600，默认见 status）
multi             # 立刻按账号表跑一轮
multi probe       # 只读演练：逐个登录体检，不提交打卡
multi force       # 跳过"今天已打过"的判断，强制跑一轮
multi probe force # 组合使用
```

`multi probe` 是最安全的验证方式：它会真的登录、真的做门户预热，
但**不会提交打卡**，用来确认每个人的账号都能正常授权。

跑完后用 `status` 看每个人的结果。

## 每个人的结果推给每个人（0.4.0 起）

给每个账号配一条**只关联他**的推送通道，他的手机上只出现他自己的结果：

```text
notify add A02url url=https://sctapi.ftqq.com/<小王的SendKey>.send style=2 accounts=A02
notify add A03url url=https://api.day.app/<小赵的BarkKey>/{title}/{body} style=0 accounts=A03
```

- `accounts=` 里写标签，逗号分隔可多选；写 `all` 表示收所有账号的结果。
- 默认那条 `notify set` 的通道收**全局事件 + 整轮汇总**（谁都没配自己通道时，结果都在它上面）。
- 每人一天只推一条「打卡成功」；失败按每 3 轮一条的节奏，不会刷屏。
- 详见 **[手机通知](notify.md)**；桌面版（`desktop/`）通知规则与这里完全一致。

## 时间预算

每个账号要经历登录 + 门户预热 + 打卡 + 复查，大约 20–60 秒。
6 个账号加间隔，一轮大概 3–8 分钟。

打卡窗口是 21:00–23:30，时间非常充裕，**不需要把间隔压到 0**。
建议间隔 20–60 秒，减少被平台风控注意的可能。

## 常见问题

| 现象 | 处理 |
| --- | --- |
| 某个人一直失败，其他人正常 | 单独 `account off` 停用他，再检查该账号的指纹和对应的微信凭据槽位 |
| 报 `NEED_MFA` | 该账号的指纹不对或已失效，让他用自己浏览器重新取一次 |
| 微信换票失败 / 找不到凭据 | 确认槽位索引与账号表顺序一致；凭据被拒绝时由该账号持有人重新获取并导入 |
| `account list` 里没有 | 检查标签拼写；`account add` 参数是否齐全（至少 5 段） |
| 想把主账号也加进表 | 可以。表非空后，`auth` 配的那个主账号**不再单独执行** |
| 全部报错 | 先 `chain 0` 确认设备本身链路正常，再排查指纹 |
| 忘记某人的密码 | 无法查看（设备只存不回显），删掉重新添加 |

## 安全建议

- 每个人只填自己的账号，密码让他自己输入，不要代填。
- 定期用 `account list` 核对，删除已经不需要的账号。
- 板子丢失或转手前，执行 `reset` 并输入 `YES` 擦除全部配置。
- `status` 与 `account list` 都会对学号打码、密码与指纹只显示「是否已设置」，可以放心截图。

## 选择部分账号执行（0.8.0）

电脑端在查询与配置中勾选目标，手机端在执行表单中勾选。登录、链路检查、打卡与演练均支持一个或多个账号；未选不执行，禁用账号须先启用。快照修订号变化会拒绝旧选择，需刷新重新确认。每人独立切换会话、票据和位置；执行后还原设备运行上下文，不改全局账号开关。
